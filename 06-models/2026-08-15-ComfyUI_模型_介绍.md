学习目标：彻底搞懂 ComfyUI 里模型到底是什么东西？它们之间是什么关系？什么时候该用哪种模型？以及下载后应该放在哪里？

还记得我们在本地运行第一个工作流的时候吗？导入工作流后，提示我们缺少模型。然后在 https://huggingface.co/Comfy-Org 仓库中找到了对应的模型文件，并进行了下载和保存。之后才能正常运行工作流。
这一章，我们就彻底把这些模型的底裤扒干净。读完这一章，你再看到模型名称、模型类型、存放路径，不会再有“我在哪、这是谁”的迷茫感。
迷茫本章节补充内容，来自于网友&nbsp;Jack Man&nbsp;的提问：模型文件名是很长的一串数字字符。这些数字字符代表什么？不同厂家的模型之间不兼容，这个容易判断。但是同一层加不同模型之间是否兼容，怎么判断？
模型的概念
还记得我们最早举例的文生图工作流的时候吗？在《ComfyUI 的灵魂拷问：工作流到底是什么？为什么它是核心？》中，我们把一个叫&nbsp;v1-5-pruned-emaonly-fp16.safetensors&nbsp;的文件拖进了&nbsp;models/checkpoints/&nbsp;文件夹，然后刷新页面，原来红色的报错框变正常了，点一下运行，图出来了。那这个模型文件到底是什么呢？
我们用拍婚纱照来举个例子，拍婚纱照得去专业的摄影馆。摄影棚里肯定不是只有一个人给你服务，而是一整个团队：有主摄影师、灯光师、道具师、化妆师、后期修图师……每个人负责一块专业活儿，合在一起才能出一张好照片。ComfyUI 中的模型，就和这个摄影团队中的成员一样，每种模型都有各自负责的内容，比如说有的模型决定整体画面的风格，有的模型负责画面的色彩调整，然后把不同类型的模型组合起来，就会生成一张符合要求的图片。好比摄影团队为什么要这么多成员一样，模型也很多的分类，对应不同的职责和功能。
那这些模型是怎么出现的呢？
一个基础模型的诞生，说白了，就是往一台超级电脑里灌大量的图片，让它自己去学规律，而这个过程就叫做训练。训练完成后，模型会以&nbsp;.safetensors&nbsp;格式发布。这种格式只存模型权重，不含可执行代码，加载快而且安全。现在新模型默认都输出这种格式。
除此之外，训练好的模型，发布方还需要决定怎么开放：
开源形式：如 Stable Diffusion 系列、Flux.1 Dev。你可以免费下载、本地部署、甚至拿去训练 LoRA。
闭源形式：如 Midjourney、Flux.1 Pro、SD3 系列。只能通过 API 调用或云端使用，要付费。
半开源：有的模型允许非商业用途免费，商业使用要额外授权。比如 Flux.1 Dev 非商业用途免费，商业用途需要单独购买许可证。
所以，一般来说，模型就是预先训练好的、来决定图像风格、质量和提示词匹配能力的神经网络权重文件，是生成图像的核心大脑。
现在，你应该明白了模型的概念。接下来，让我们认识一下这支“画家团队”的每一位成员。
模型抽象分类详解
这一节的内容前期学习的时候了解即可，不需要记忆。
我们可以把 ComfyUI 里所有的模型类型分成四大类，大家没有接触也可以大致了解一下对应的功能，有点点还是很有必要去看的。
核心主创：离了他们，一张图都出不来
这一组是生成图片的基本要素，缺任何一个，工作流要么报错，要么出鬼图。文生图工作流中，将正面提示词清空，然后点击运行，就会出现这种抽象图片了。
抽象图片checkpoints： 这里存放的是把&nbsp;Diffusion Model（底模） + 文本编码器（CLIP/T5）+ VAE&nbsp;整合后的模型，这类模型决定了整幅画的风格是哪一种？写实照片、二次元动漫、油画质感、3D渲染……这个模型也被称为全家桶模型（就是整合包形式的模型，后面的章节中有介绍）。融合模型的体积一般很大，动辄几个G。存放路径为：ComfyUI/models/checkpoints/。clip / text_encoders： 这里面的模型负责把自然语言翻译成模型能识别的专业数字指令。通俗的说就是我们在提示词框中输入 a cat（一只猫），这个模型就负责把这句话转换成数学信号然后交给底模（Diffusion Model）。这些模型的能力是有强弱之分的，越强的模型对文字描述的转换越精准，生成的内容更符合预期。再者，部分模型训练的时候数据里面没有中文，所以仅仅支持英文提示词，强行输入中文提示词的话，影响效果可能很微弱甚至随机甩图。这些模型的存放路径为：ComfyUI/models/clip/&nbsp;和&nbsp;ComfyUI/models/text_encoders/。这里你可能有点疑惑了，既然功能是一样的，为啥整两个文件夹保存呢？其实它们里面放的模型本质上就是一个东西，只不过因为早期专门存放 clip 模型就叫做 clip，后来逐步加入了一下其他大模型，再放到 clip 里面就不合适了，干脆新建了一个文件夹 text_encoders 来存放这些新的模型，根据名称也很好理解就是文本编码。最后你不难发现，不管你是将文本编码类型的模型放到哪个文件夹中，最后&nbsp;加载CLIP&nbsp;节点都能加载出来。推荐将该类型模型放到&nbsp;text_encoders&nbsp;目录中。clip和text_encoders目录通用vae： 主要用来将潜空间之间的内容转换成可见图片，这类模型直接影响画面的色彩饱和度、明暗对比和细节锐利度等。存放路径为：ComfyUI/models/vae/。diffusion_models / unet： 这类模型是真正干活的模型，也是我们的底模。他负责在画布上一遍遍涂抹、修改，把一团随机噪点反复打磨成清晰的画面。在一些新架构里，这个岗位被单独拆成了一个模型文件。存放路径为：ComfyUI/models/diffusion_models/&nbsp;或&nbsp;ComfyUI/models/unet/。这里也是同样的问题，为什么有两个文件夹？其实这个也很容易理解，unet 目录中存放的是传统 UNet 模型（如 SD 1.5），而 diffusion_models 目录中存放的则是新一代 Transformer 架构 （如 Flux）模型。好比新能源汽车的出现，原来的汽车停车场因为没有充电桩不能满足新能源汽车的需求了，干脆就新建一个停车场专门给新能源车型用。现场指导：让画面听你的话
核心主创角色负责图像骨架的搭建和底片的去噪生成，那接下来的现场知道这一组则是负责对图片进行精装修和现场调度，让画面按照你的想法（提示词）来。
loras： LoRA模型的文件一般情况下不会很大，几十MB到几百MB，它的作用就是给底模赋予一种专精画风，比如在底模的基础上挂一个动漫风格的 LoRA 模型，底模生成的图片经过 LORA 模型后就会成动漫风格。我们甚至可以通过串联的方式给底模挂多个 LoRA，来生成多种风格融合的图片。LoRA 模型的存放路径为：ComfyUI/models/loras/。controlnet： 这类模型的作用就是给画面固定骨架。它能根据你给的参考图（比如人体骨骼图、边缘线稿、深度图等），把构图、人体姿势、物体轮廓牢牢锁住，防止底模自由发挥。存放路径为：ComfyUI/models/controlnet/。embeddings： 这类模型文件通常只有几 KB 到几十 KB，更像是一个小助手。当你在提示词通过某个单词（比如&nbsp;*cat_style*）触发它的规则时，它就会立刻激活某个特定概念或风格。就像给图片生成过程增加了一个快捷指令。存放路径为：ComfyUI/models/embeddings/。style_models： 这类模型专门负责整体画风切换，比如 T2I-Adapter。和 LoRA 有点类似，但是专注于整体艺术风格的迁移，而不是像 LoRA 那样关注具体角色或物体。存放路径为：ComfyUI/models/style_models/。另外几个分类用的比较少：例如超网络（Hypernetwork）是早期的一种微调方式，基本被 LoRA 取代了；模型补丁（Model Patches）是技术层面的小修补，日常用不到。新手了解一下名字就行。
后期修图：让作品更精致
当底模生成图片之后，后期修图模型这一组则专门用来负责对图片或视频进行后期修改，比如放大、补帧等操作。
upscale_models： 这个目录用来存放专门把低分辨率小图放大成高清大图的处理模型。普通放大只会变模糊，但这类模型能脑补出更多细节，让模糊的图变清晰。存放路径为：ComfyUI/models/upscale_models/。latent_upscale_models： 也是存放做放大的模型，但这一类模型直接在潜空间里操作，不用先把图画出来。优点是速度快、显存占用低。存放路径为：ComfyUI/models/latent_upscale_models/。frame_interpolation： 存放视频补帧相关的模型，在做视频的时候用的。在两帧画面之间插入中间帧，让原本卡顿的动画变得流畅顺滑。存放路径为：ComfyUI/models/frame_interpolation/。vae_approx： 这个文件夹中存放的是一种特殊的轻量化/近似VAE模型，可以理解为就是 VAE 模型的精简版。完整的 VAE 模型占用显存大，计算量高。而用这个下面的模型则可以降低显存占用和计算工作量，出图更快，但是最终的画质可能有损失，说白了就是在性能和质量之间做个取舍。存放路径为：ComfyUI/models/vae_approx/。特殊工种：配套的特殊能力
这一组模型并不直接参与画画，但是又不可获取，因为这些模型提供了各种配套能力。
audio_encoders： 多用来给画面配声音，用于嘴型同步、音乐律动等。存放路径为：models/audio_encoders/。clip_vision： 让底模能看懂一张参考图，用于反推提示词或风格迁移。存放路径为：models/clip_vision/。gligen： 基于边界框的布局控制，比如“左上角放一只猫，右下角放一张桌子”。存放路径为：models/gligen/。photomaker： 用几张人脸照片，生成这个人各种风格的图像。存放路径为：models/photomaker/。background_removal： 专门移除图像背景，比如 RMBG 类模型。存放路径为：models/background_removal/。LLM： 辅助生成或优化提示词，可以用本地大语言模型来帮你写更专业的描述。存放路径为：models/LLM/。optical_flow： 计算像素的运动轨迹，辅助视频补帧和稳定。存放路径为：models/optical_flow/。diffusers / configs： 存放 Hugging Face 一些比较特殊的模型和配置文件，一般情况下会自动生成，不用手动操作。存放路径为：models/diffusers/、models/configs/。模型文件的下载
常见文件格式
在下载模型时会看到各种后缀名，这些不同的后缀名就代表了各种不同的格式。我们可以以&nbsp;CLIPLoader&nbsp;为例，查看官方文档，它在“Supported model formats”一节明确列出了所有支持的格式。
英文版链接：https://docs.comfy.org/built-in-nodes/ClipLoader#cliploader-comfyui-built-in-node-documentation
中文版链接：https://docs.comfy.org/zh/built-in-nodes/ClipLoader
官方文档中列出的格式如下：.ckpt、.pt、.pt2、.bin、.pth、.safetensors、.pkl、.sft、
关于&nbsp;.gguf&nbsp;格式的官方说明：需要补充的是，官方原生并不支持.gguf&nbsp;格式，并且明确指出需要通过安装第三方插件（如 ComfyUI-GGUF）来加载这种格式地模型。相关说明链接：https://docs.comfy.org/faq/models
那这些格式分别有什么特点呢？我们接着往下看：
.safetensors： 这种格式是目前最主流、也是官方最推荐的格式。它的最大特点是安全性。模型文件里只有模型权重，没有任何可以执行的代码，因此加载的时候不需要加载执行代码。现在新发布的模型，基本上都是这个格式。.ckpt： Stable Diffusion 早期的标准格式，它的特点是完整性强，安全性和加载速度稍逊一筹。如果同一个模型同时提供两种格式，肯定优先选择&nbsp;.safetensors&nbsp;版本。.pt&nbsp;/&nbsp;.pth&nbsp;/&nbsp;.bin：这种格式已经比较少见了，但是偶尔也会出现，.pt&nbsp;和&nbsp;.pth&nbsp;是比较常见格式。.pt2&nbsp;/&nbsp;.pkl&nbsp;/&nbsp;.sft：.pt2&nbsp;是新版 PyTorch 格式、.pkl是传统序列化文件、.sft则是同系格式。这些在日常下载中不常见，初学者看到时知道它们可以被 ComfyUI 识别就行。.gguf： 官方原生并不支持&nbsp;.gguf&nbsp;这种格式，并且明确地指出需要安装第三方插件（如 ComfyUI-GGUF）才能加载这种格式地模型。所以日常下载时，闭着眼睛选&nbsp;.safetensors&nbsp;格式就对了。
模型的打包方式
当你下载一个底模文件时，可能会遇到下面这三种不同打包方式对应的模型。
方式一：完整包（All-in-One）
特点：一个&nbsp;.safetensors&nbsp;或&nbsp;.ckpt&nbsp;文件里，同时包含了UNet、CLIP、VAE。你只需要下载这一个文件，放到&nbsp;models/checkpoints/&nbsp;下，Checkpoint加载器（简易）&nbsp;节点就能把它拆成MODEL、CLIP、VAE 并提供三个对外地输出端口给下游节点使用。
完整包加载器优点：一个文件包含了所有，不用分别下载 CLIP 和 VAE，且这个包含是模型发布者经过测试的，不存在兼容性的问题。
缺点：文件体积大（因为包含了三种类型地模型）。而且如果你只想换一个文本编码器（比如把英文翻译官换成中文翻译官），没法单独换，必须重新下载整个包。
典型代表：我们一直在用的 SD1.5&nbsp;v1-5-pruned-emaonly-fp16.safetensors&nbsp;就是完整包。SDXL 的很多模型也是完整包。
方式二：分体包（Separate Files）
特点：UNet、CLIP、VAE各自独立成文件。你需要分别在&nbsp;models/diffusion_models/（新架构）
&nbsp;或&nbsp;models/unet/（旧架构） ，`models/clip/&nbsp;或&nbsp;models/text_encoders/，models/vae/&nbsp;中分别保存这三种类型地模型文件。然后工作流里不再用&nbsp;Checkpoint加载器（简易），而是用&nbsp;UNet加载器+&nbsp;CLIP文本编码&nbsp;+&nbsp;加载VAE，再把它们手动连线到 K采样器和 VAE解码等节点。
优点：这样拆开地有点就是可以单独升级或替换某一个模型，比如 UNet 用 A 模型，翻译官用 B 模型。
缺点：缺点也很明显，就是一次要下载三个模型文件。
典型代表：Flux、SD3、Wan 系列的新模型通常以分体包形式发布。在 HuggingFace 上就能看到&nbsp;flux1-dev.safetensors（UNet）、clip_l.safetensors（CLIP）、ae.safetensors（VAE），就是分体包。
方式三：半完整包（Partial All-in-One）
特点：一个文件里包含了UNet + CLIP，但 VAE 单独提供。或者包含UNet + VAE，text_encoders&nbsp;单独提供。这种比较少见，通常是社区用户重新打包的。
优点：介于两者之间，省一点事。
缺点：不是标准用法，容易搞混，所以并不推荐。
对新手的影响
你现在用的是 SD1.5 的完整包，所以一直用的&nbsp;Checkpoint加载器（简易）&nbsp;节点，一拖三，简单省事。等以后想玩 Flux 或 Wan 这些新模型时，你会发现它们大多采用分体包形式，需要用&nbsp;UNet加载器&nbsp;+&nbsp;CLIP文本编码&nbsp;+&nbsp;加载VAE&nbsp;分别加载，然后手动连线。
你现在只要知道不是所有模型都能用一个&nbsp;Checkpoint加载器（简易）&nbsp;节点就能加载的。如果你拖进去一个分体包的模型文件，Checkpoint加载器（简易）&nbsp;会报错，因为它找不到同一个文件里的 CLIP 和 VAE。
模型文件：名称详解
通过上面的介绍，你已经知道了模型是什么？模型打包方式有哪些？但是当你打开下载网站，看到像&nbsp;hunyuan3d-dit-v2-mv-turbo_fp16.safetensors&nbsp;这样一长串文件名时，是不是又有点懵？因为压根不知道这个模型是干啥的？有什么作用？
问题不大！这一节，我们就来了解模型的身份识别大法。学会之后，你看到任何一个模型文件名，都能在几秒内说出：它叫什么、是哪个流派的、有什么特长、该用多少步采样、甚至能不能商用都一清二楚。
第一层：基础身份
我们先用几个简单的例子建立基本的认知。
ae.safetensors：一般情况下，ae 指的就是 VAE 的模型文件。
z_image_turbo_bf16.safetensors：名为&nbsp;Z-Image，turbo&nbsp;表示加速版，bf16&nbsp;表示精度。
qwen_3_4b.safetensors：通义千问第3代，40亿参数规模。
从这三个例子的学习中，我们可以总结出这套最基本的命名规律：
名称：ae、z_image、qwen，这些都是告诉你它叫什么名字，可能会包含模型的厂家、版本号等内容。
版本号：qwen_3&nbsp;中的&nbsp;3，表示的就是发布的第几代，就好比 Windows 型号 7\10\11等，数字越大技术越新。
特殊标记：turbo，通常代表蒸馏加速版，采样步数更少、生成更快。
参数：4b&nbsp;= 40亿参数。参数越多，能力越强，但也越吃显存。1b = 10亿。
精度：bf16&nbsp;/&nbsp;fp16&nbsp;/&nbsp;fp32，字母后面的数字越大精度越高，文件也越大。bf16&nbsp;是当前主流的高性价比选择，同时兼顾了精度和体积。
格式：.safetensors&nbsp;是目前最主流、最安全的格式，闭着眼睛选它就行。
第二层：架构与版本标签
再来看一个更复杂的名字：hunyuan3d-dit-v2-mv-turbo_fp16.safetensors：
hunyuan3d：表示模型的系列或者模型名称，这里指的是混元 3D 系列。
dit：标注这个模型的架构是新一代 DiT（Diffusion Transformer）架构，与 Flux、SD3 同流派。
v2：当前模型的版本号，表示是这个模型的第二代产品。
mv：表示这个模型具有某种能力，mv 是 Multi-View 的首字母缩写，表示多视角生成。
turbo：加速版模型，表示是蒸馏版，少步数快速出图。
fp16：模型精度。
.safetensors：模型文件格式，表示是安全权重文件。
为什么“架构”信息很重要？
因为它直接对应前面学过的“画派”和“加载方式”：
看到&nbsp;dit、diffusion_transformer&nbsp;就是 16 通道画派；SD1.5/SDXL 就是 4 通道画派。16 通道画派： 包括 SD1.5、SDXL等模型，这类模型一般发布较早，模型文件较小。它们的 text_encoders、vae、diffusion_models 用的都是同一套接口规格。16 通道画派： 包括 Flux、SD3 系列，这类模型一般发步较新，且模型文件相对而言比较大。它们用了更先进的 16 通道潜空间技术，接口规格完全不同。同一个画派内的底模可以自由切换：比如 SD1.5 的工作流，完全可以换成 SDXL 的底模可。但你绝对不能把 SDXL 的 底模换成 SD3 的底模，因为接口对不上，执行就报错。所以下载模型的时候，要通过文件名、模型介绍等内容来看看和主模型是不是兼容，这是避免出现模型兼容性的最基础的一步。因为它们的“接口规格”完全不同——潜空间的通道数、嵌入维度、token 编码方式都对不上。为了方便理解这句话中的几个概念，这里再多几句嘴：
What潜空间的通道数：不同宽度的“信息高速公路”
简单说，就是模型内部用来承载图像信息的“特征图”有多少个图层。你可以把它想象成高速公路的车道数——车道越多，一次能并排运输的信息种类就越多。
4通道画派 (SD1.5, SDXL)： 它们的 VAE 会把RGB（3通道）图像压缩到一个只有&nbsp;4个通道的潜空间里。这4个通道各有分工，一个通道可能主要存“结构”，另一个存“纹理”，但细节相对抽象。16通道画派 (Flux, SD3)： 它们的 VAE 压缩能力更强（或者压缩策略不同），用一个&nbsp;16通道的潜空间来存储信息。这就像从4车道拓宽到了 16 车道，可以并行承载更丰富、更细致的信息（比如更精确的边缘、材质、光影分解）。16通道画派 (Flux, SD3)： 它们的 VAE 压缩能力更强（或者压缩策略不同），用一个&nbsp;16通道的潜空间来存储信息。这就像从4车道拓宽到了 16 车道，可以并行承载更丰富、更细致的信息（比如更精确的边缘、材质、光影分解）。因为 UNet 或 Dit 架构的模型，其内部的每一个卷积层、注意力层的输入和输出通道数都是硬编码在模型权重里的。如果把一个4通道的潜空间张量（形状：[B, 4, H, W]）强行喂给一个为 16 通道输入设计的模型，模型会试图去读取第 5 到第 16个 通道的数据。但这些通道根本不存在，程序会立刻报维度不匹配的错误。
嵌入维度：文本与图像交流的“语言长度”
这是指文本编码器（如CLIP、T5）把每个词语转换成的词向量的长度。这个向量是模型理解语义的核心。可以把它想象成文本模型使用的“单词”本身的详细程度。
SD1.5 (CLIP)： 其文本编码器输出的词向量维度是&nbsp;768。SDXL (两个CLIP)： 一个输出768维，另一个输出1280维，然后组合使用。Flux/SD3 (T5 + CLIP)： T5模型的输出维度可以非常大（比如4096维）。生成模型 UNet/Dit 中的交叉注意力层，是连接文本和图像的“翻译官”。它要求输入的文本嵌入向量的长度（维度），必须和其内部预设的输出维度参数完全一致。如果维度不匹配：Flux&nbsp;的交叉注意力层期望收到一个&nbsp;4096维&nbsp;的向量来理解复杂描述。你塞给它一个&nbsp;768维&nbsp;(来自 SD1.5 CLIP) 的向量。就像你请一个精通复杂工程图纸的专家（4096维），却只给他一张便利贴（768维）。他看不懂，而且更关键的是，数学运算上维度对不上，程序会因矩阵乘法不兼容而崩溃。
Token 编码方式：文本的“语法与字母表”
这是文本编码器将原始句子分解成Token（可理解为词片段）的方式，以及如何给这些Token编号。它包括：
分词器： 用什么规则切分单词。例如，“unhappiness”&nbsp;可能会被一种分词器切成&nbsp;[“un”， “happiness”]，被另一种切成&nbsp;[“unha”， “ppi”， “ness”]。词表： 一共有多少个不同的Token ID。特殊Token：&nbsp;[CLS]、[SEP]、[EOS]&nbsp;等标记的含义和用途不同。模型是根据它在训练时见过的Token ID表来学习的。如果用T5的分词器（大词表、不同的切词规则）把一句话转成一组 Token ID，然后喂给 SDXL 的 CLIP文本编码器。CLIP 会看着这些它根本不认识的 ID 号（例如，T5里的第 100000 号 Token，在 CLIP 词表里可能是空白或代表“马”），输出完全乱码的文本嵌入。即便勉强不出错，模型也无法理解这个乱码嵌入的意思，生成的结果会是毫无意义的噪声。
所以，同画派才兼容的根本原因就是：模型在训练时，其权重参数已经与特定规格的“数据接口”深度绑定。跨画派混用，就如同给汽油发动机加柴油，物理上（通道数）和化学上（嵌入/编码方式）都无法工作。
逐层判断的具体方法
针对每个“工种”（模型类型），判断同一层不同模型是否兼容，需要看以下维度：
1. 底模之间的互换
Checkpoint 之间不需要“互相兼容”——因为它们本身就是互斥的，你一次只用一个主模型。但如果你想判断模型 A 能不能替换模型 B，看两点：
架构系列： SD1.5 系的 Checkpoint 可以互相替换，SDXL 系的互相替换，Flux 系的互相替换。跨系列不能。文件名中的架构标识： 看到&nbsp;dit、diffusion_transformer&nbsp;就是 16 通道画派；SD1.5/SDXL 就是 4 通道画派。2. VAE 与 Checkpoint 的搭配
判断方法：VAE 必须和 Checkpoint 属于同一个画派。
SD1.5 的 VAE（4 通道）只能用在 SD1.5 / SDXL 的 CheckpointFlux 的 VAE（16 通道） 只能用在 Flux / SD3 的 Checkpoint强行搭配：在潜空间中，编解码维度不匹配，会出现画面色彩怪异、物体扭曲等情况。实际操作中就是看 VAE 文件名里是否带&nbsp;flux、sd3&nbsp;等关键字，或者看它是和哪个 Checkpoint 一起发布的。
3. CLIP / Text Encoder 的兼容性
判断方法：看模型架构和语言能力
模型架构： CLIP 必须和 UNet/Diffusion Model 的架构能够匹配。Flux 用的是&nbsp;clip_l&nbsp;+&nbsp;t5xxl&nbsp;双编码器组合，SD1.5 用的是&nbsp;clip-vit-large-patch14&nbsp;单编码器，不能混用。语言能力： 英文 CLIP 只能听懂英文；中文友好模型（如 Qwen-Image、ERNIE-Image）自带中文编码器，可以直接输入中文也可以输入英文。如果你给英文 CLIP 强行输入中文提示词，结果会“词不达意”。实操技巧：
分体包发布时，一般情况下，都会提供配套的模型集合，就好比翻译官和主画师是配套的，不要擅自换。文件名里有&nbsp;qwen、ernie&nbsp;的是中文支持中文的。clip_l、clip_g、t5xxl&nbsp;这些名字代表了不同的 CLIP 型号，要和对应的 Checkpoint 搭配。4. LoRA 与底模之间的兼容性
判断方法：LoRA 必须和它训练时用的基础模型同架构。
为 SD1.5 训练的 LoRA 只能用在 SD1.5 的 Checkpoint 上为 SDXL 训练的 LoRA 只能用在 SDXL 的 Checkpoint 上为 Flux 训练的 LoRA 只能用在 Flux 的 Checkpoint 上为 ControlNet 的兼容性
判断方法：和 LoRA 一样，ControlNet 也是绑定基础模型架构的。
SD1.5 的 ControlNet 配 SD1.5 的 CheckpointSDXL 的 ControlNet 配 SDXL 的 Checkpoint快速判断的“四步法”
拿到一个模型文件，想知道它能不能和你已有的模型搭配，走这四步：
第一步：看文件名里的画派标识
flux&nbsp;/&nbsp;sd3&nbsp;/&nbsp;dit&nbsp;→ 16 通道画派sdxl&nbsp;→ SDXL（4 通道画派）sd1.5&nbsp;/&nbsp;sd15&nbsp;→ SD1.5（4 通道画派）什么都没写只能去下载页面看说明第二步：确认目标模型类型（是什么工种）
Checkpoint/UNet 放&nbsp;checkpoints/&nbsp;或&nbsp;unet/VAE 放&nbsp;vae/，必须和 Checkpoint 同画派CLIP 放&nbsp;clip/，必须和 Checkpoint 同架构LoRA 放&nbsp;loras/，必须和目标 Checkpoint 同架构ControlNet 放&nbsp;controlnet/，必须和目标 Checkpoint 同架构第三步：确认同画派 → 可以搭配
第四步：确认不同画派 → 直接放弃，别试（100% 报错或出鬼图）
重要补充
SD1.5 和 SDXL 虽然都是 4 通道，但 LoRA/ControlNet 不通用。因为它们的 UNet 结构不同（SDXL 多了一个&nbsp;text_encoder_2），所以 SD1.5 的 LoRA 不能用于 SDXL，反之亦然。前面说的“同画派内可互换”主要是指 VAE 这个层面。精度不影响兼容性。模型文件名中的&nbsp;fp16、bf16、fp8&nbsp;只影响显存占用和精度，不同精度的同模型可以互换使用。GGUF 格式支持（如 ComfyUI-GGUF），这种格式的模型文件不能直接用 ComfyUI 内置的加载器进行加载，需要结合第三方插件使用。（这个点在后面的章节中会有详细的说明）用一句话总结就是：判断同一层模型是否兼容，就是确认它们是否共享同一个底层架构（画派）。画派相同的时候大概率是兼容的，画派不同那肯定是不兼容的。画派信息藏在文件名、下载页面、以及模型发布的基本说明里。
